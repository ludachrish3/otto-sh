
# Goal

I'd like to do a fairly serious overhaul of the "Getting Started" section of the documentation. I went through it manually for the first time, and I think that it can be improved in a number of ways. It's VERY IMPORTANT THAT THERE ARE DOCS TESTS to verify the setup procedures so that users are not led astray

## Subpages covering a worked example

There are pretty common steps that will almost always be followed when setting up otto. The goal here is not to introduce more duplication, but rather to provide a concrete example of how a project would be set up. I'd like the worked example in the docs to also be documentation tested against the real test bed to show real output from the different OSes and to explain the logic and placement configuration.

The existing pointer to installation is fine and can remain on the "Getting Started" main page. The current info about otto init is also okay, but is possibly duplication of the `otto init` CLI page? A tiny bit of text and a simple pointer in the main page would be okay

### Desired Subpages

I'd like the worked example to basically walk through the steps it would take to define the unix and embedded labs from scratch.

#### Defining Hosts

Defining hosts is the most basic thing that's required to run otto. Documentation about gather info and populating it is crucial. The workflow I ended up with was: define host names, IPs, creds, hops, and OSes. Then use the `otto host probe` command to find out more about the hosts. Setting up the inventory is also a part of defining hosts now. The lab definition step might merit some subpages of its own to go through what an inventory is and its scope, what the host definitions cover, and the JSON to NetBox/database growth path. This request also brings up a number of enhancements about `otto host probe`:

* Doing a bit more recon for open ports to guess at available protocols would be very helpful.
* Busybox commands to measure sockets sometimes do not match. It's worth doing a once-over for the default metrics for all OS profiles and have per-profile defaults that line up with the majority of versions rather than have a single one for all unix-based hosts.
* I noticed some fields in the userland_options that seem similar to True and False. Should some options be boolean flags, or do we need more than 2 values to indicate support?

##### Unix

Describe any settings specific to Unix (this is likely fairly slim). Make a recommendation for whether the `otto host probe` command is really needed. I would guess that older Unix hosts would still benefit from a probe command.

##### Busybox

Describe any settings specific to BusyBox.

##### Zephyr

This is one of the more important OSes because it is so likely to need customizations and tweaks. Showing how probe and attempting to connect with the default host class with the log level set to debug to figure out how the CommandFrame should be defined is EXTREMELY crucial. Defining the oldest Zephyr host, which requires customization is very hepful so that users can see what they need to define and how.

#### Defining customizations

The goal is for monitoring to successfully capture all default statistics for all hosts. Zephyr's SNMP is also interesting, so hopefully that can proveably have some support for monitoring. Showing how to override aspects of each host, like:

* login proxy
* post-connect actions (set shell prompt to a custom prompt)
* add performance metrics
* modify performance metric commands and/or parsers

NOTE: A goal (not necessarily now) is to down-select the monitor commands to reduce the burden or focus only on specific stats on certain runs. This down-selection needs to be supported via the `otto monitor` command and when running `otto test --monitor` (possibly by adding a `--monitor-stats` argument).

#### Defining the boards of interest

Need to show a way to provide a regex for boards of interest for a repo. The example should choose all of the busybox hosts. Also explain how this affects the `all_hosts()` and `do_for_all_hosts()` generators.

### Issues

I noticed that some fields were not covered at all in the hosts README.md file that gets generated by `otto init`. It provided the highlights, but there were multiple gaps that made getting started somewhat challenging.

The JSON schema also didn't have all the fields in it, which made using VSCode to autocomplete entries difficult. I'd really like code snippets to be available for host entries to prepulate all of the required fields to make the startup much easier.

`otto init` provides partial steps for enabling tab completion. Both steps (`otto --install-completion` and `source ~/.bash_completions/otto.sh`) should be in the `otto init` output.

Separately, the host's schema should be reconsidered. I noticed that there's lots of duplicated element info in each host, like `element_id`. I'm thinking that we might want to add a new level above "hosts", named "elements" that has a list of hosts inside it. This way there's more clear structure, less data duplication, and `element_id` has a more appropriate home.

I'm also reconsidering making hosts all strict pydantic models. It's quite possible that elements and hosts could have custom metadata that users would like to track. What are the best ways to accomodate this? Should we allow for composition of lab data, with dicts from all lab backends effectively being `update()`-ed to compose a final lab. This could be error prone, so I'm not totally sold on this approach, but we need to allow for host-, element-, and lab-level metadata. It's possible that there should be a separate labs dict. It's hard for me to tell if this design fully holds together, so I'd like to talk through corner cases of this before committing to any large changes.

The introduction of the elements layer to the dict seems pretty solid to me, but I still want your input.
