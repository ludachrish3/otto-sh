# Release-notes pages in the docs

**Status:** approved approach (Chris, 2026-11-18: footer rule going forward,
historical breaks kept with a note). Reviewed by Astra and Opus. Rulings folded
in (Chris, 2026-11-18): maintainer scopes are dropped from the notes only;
footerless rows show the commit body, collapsed.

## Intent

Users should learn what each otto release brought from otto's own
documentation, without visiting GitHub: its new features, its bug fixes and,
above all, every breaking change and what to do about it. The pages are
produced by machinery from the commit history and never written by hand, so
they cannot drift from what shipped.

## Goals

- A **Release notes** entry under the docs' *Reference* caption
  (`docs/index.rst`), at `docs/release-notes/`, a sibling of `docs/cli/`,
  `docs/configuration/` and `docs/api/`.
- **One page per release, from 0.16.0 on** (Chris, 2026-11-18). That means
  every tagged release git-cliff renders in CHANGELOG.md whose version is at
  least the renderer's `FIRST_RELEASE = "0.16.0"`, newest first, in
  git-cliff's order (never a string sort: 0.9 before 0.10). The floor is
  fixed, not a rolling window: releases ship about weekly, so a window of 10
  would reach back only two months and delete a page with every release.
  Earlier releases get one index line pointing at CHANGELOG.md.
- Each page has, in the order Chris asked for:
  1. A one-line lead naming how many breaking changes the release has, with a
     link to that section, or saying there are none.
  2. **New features**: commits git-cliff groups as `Added`.
  3. **Bug fixes**: commits git-cliff groups as `Fixed`.
  4. **Breaking changes**: a summary table of every user-facing breaking
     event, then one entry per break carrying its full remediation text.
- Maintainer-only commits do not appear on the pages: not in the lists and
  not in the breaking section. CHANGELOG.md and the version census are
  unchanged (Chris, 2026-11-18).
- **From now on every breaking mark carries its remediation.**
  `make check-breaking` refuses a counted mark in the landing range that has
  no real `BREAKING CHANGE:` / `BREAKING-CHANGE:` text. That covers the
  pre-push hook and CI's `lint-python`. "Real text" is defined below.

## Non-goals

- No hand-written prose, highlights or migration guides.
- `Changed`, `Documentation`, `Dependencies` and `Maintenance` bullets are not
  listed. A user-facing breaking commit in one of those groups is still in the
  breaking section.
- No *Unreleased* page.
- No rewriting of published history, and no retroactive refusal of published
  commits.
- CHANGELOG.md's content, `cliff.toml` and the GitHub release body don't change.

## Anti-goals

- **A second parser or a second verdict.** Grouping comes from git-cliff.
  Commits, footers, the breaking verdict, corrections and the new
  "unremediated" verdict come from `scripts/release_events.py`
  (AGENTS.md, "one decision, one place"). The renderer never reads git-cliff's
  `breaking_description`, which is truncated, and never re-splits a
  `raw_message`.
- **Silently dropping a footerless break.** It still gets an entry.
- **Text that renders differently from what was written.** `<host>` must not
  vanish as raw HTML.
- **A docs build that quietly renders empty or stale pages.** A shallow
  checkout fails the build, and a new tag rebuilds the HTML.

## Approaches considered

1. **Build-time renderer over `git-cliff --context` and `release_events`
   (chosen).** Each decision keeps one source, the pages can't be stale, and
   it fits `docs/conf.py`'s `_RENDERED_PAGES`. The cost is that docs builds
   need full history with tags (GitHub CI, release.yml and Read the Docs).
2. **Committed pages regenerated by `make changelog` / `make release`.**
   These work in shallow checkouts. They were rejected because they are a
   second generated artefact and bring a staleness failure mode that the
   chosen approach doesn't have.
3. **A second git-cliff template rendering Markdown.** Rejected because it
   can only reach the truncated `breaking_description`.

## Design

### `scripts/release_events.py`: the shared model grows

All of these are additions next to the parser. The existing contract stays:
`Footer.value` is the first line, and correction validation keeps reading it.

- **Full footer text.** A function returns every `BREAKING CHANGE` /
  `BREAKING-CHANGE` footer of a commit with its full value. That includes the
  continuation lines `_parse_footers` currently discards, up to the next
  footer token. Without it, `ad0edab3` loses "Drop the prefix…" and two more
  instructions. The text is taken from the same parse `_parse_footers` does,
  not a second scan: either `_parse_footers` records each footer's full span
  while `Footer` keeps its first-line `value`, or something equivalent.
- **The swallowed-trailer case.** An empty `BREAKING CHANGE:` takes the next
  non-blank line as its value (`release_events.py:203-210`). On agent commits
  that line is `Assisted-by: …`. A breaking footer whose taken value is itself
  footer-shaped (a line that would open a footer) carries **no remediation**.
  This verdict lives here, beside the parser.
- **`Events.unremediated`.** A new field lists the counted breaking events
  with no remediation text: no breaking footer, an empty one, or only
  swallowed trailers. It is **not** a `Refusal`. If it were, `release_bump`
  and `make release` would refuse 0.21.0 outright, because main already holds
  cf2f15c4b (#993) and 4bb4e37ac (#994) without footers. Only the checker
  refuses on it.
- **Maintainer scopes.** One declared set (e.g. `MAINTAINER_SCOPES`) lists
  the conventional-commit scopes that name maintainer tooling: `test`,
  `tests`, `scripts`, `gate`, `gates`, `make`, `makefile`, `lab`, `labs`,
  `bed`, `chaos`, `ci`, `lint`, `lint-arch`, `quality`, `release`,
  `changelog`, `import-budget`, `budget`, `matrix`, `vagrant`, `nightly`,
  `nox`, `githook`, `githooks`, `lanes`, `lease`, `stability`, `spec`,
  `specs`, `plans`, `plan`, `todo`, `agents`, `contributing`. The final list
  is the builder's, checked against `git log` scope counts. A commit is
  maintainer-only when its scope, or every scope in a comma list, is in the
  set. An unscoped commit is user-facing. A new maintainer scope is added
  here. The docs' contributing section names this home. The renderer is the
  only reader today, and it is the same rule as contributing.md's
  "maintainer tooling is never breaking".
- **A message-to-Commit seam.** If the renderer needs one, it uses a
  function extracted from `_parse_log`, which keeps the `separated` rule. The
  renderer gets its commits through `release_events(repo, range)` and
  `read_commits` instead, so it doesn't need one (see below).

### Renderer: `scripts/render_release_notes.py`

- **Input.** It runs `git-cliff --context --offline` once, from the repo
  root, and finds git-cliff the way `release_bump.py` does. For each release
  in the context, it calls `release_events(repo, "<prev>..<tag>")`. For the
  first tag, which has no predecessor, the range is the tag alone, i.e. its
  full history. It joins git-cliff's commits to the model's by full sha:
  - the group comes from git-cliff;
  - everything else comes from the model.

  Historical `Refusal`s never fail the docs build. A refused correction is
  rendered as an ordinary entry without a "corrects" line.
- **Which releases.** Every release in the context, in context order. A
  release whose version is not `v<X.Y.Z>` (optionally with an `rcN` suffix)
  is an error naming the tag ("delete the stray local tag"). Here is why:
  `cliff.toml`'s `tag_pattern` is read as an unanchored regex by git-cliff
  and as a glob by git (`release_events.release_tag_glob`), so anchoring it
  would break the glob reader. A stray local tag such as
  `pre-squash-exec-cli-verb` also steals commits from the real release in
  git-cliff's grouping, so the honest answer is to refuse, not to filter.
  CI and Read the Docs never carry such tags. Releases below
  `FIRST_RELEASE` are read for corrections but get no page.
- **Errors (exit 1, with the fix named):**
  - git-cliff missing or failing;
  - no tagged release;
  - `git rev-parse --is-shallow-repository` is true ("fetch full history
    with tags").
- **Output.** It writes `docs/release-notes/<X.Y.Z>.md` per release (the
  leading `v` stripped) and `docs/release-notes/index.md`. It deletes any
  other `*.md` in that directory. `--check` renders to memory and writes
  nothing, like `render_proven_range`.
- **Lists.** Each bullet is `**scope**: subject`, the subject line as
  CHANGELOG.md shows it. A breaking bullet links to its entry. Maintainer-only
  commits are left out.
- **Breaking section.**
  - **Summary table:** Change (`scope: subject`, linked to its entry) and
    Kind. Kind is plain words derived from the git-cliff group (feature,
    fix, change…), not Keep a Changelog's headings.
  - **One entry per break.** Each has a heading and a meta line with the
    short sha linked to GitHub (a reference, not the only source). The body
    is the full remediation text, in footer order.
  - **A footerless or unremediated break** says *No remediation was recorded
    for this change*. A collapsed block below that holds the commit's body
    from git, with trailers (`Assisted-by:` etc.) left out. The builder picks
    the collapsible construct (sphinx-immaterial collapsible admonition, or
    `<details>`) and checks that it builds under `-W`.
  - **A correction** says which earlier commit it marks, as CHANGELOG.md
    does. The corrected commit's own release page gets a note on that entry
    saying a later release marked it breaking, with a link.
  - **Anchors** are keyed on the short sha. They are globally unique, so
    `-W` never sees a duplicate label.
- **Escaping.** Footers and subjects are Markdown by contract: contributing.md
  says so, because backticks are used throughout history. Raw HTML is never
  passed through. `<word>` renders as literal text, outside code spans too.
  The builder chooses the mechanism (MyST config or escaping in the renderer),
  proves it on `label runs <host>/<product> (#790)` and on f47d617f6's
  indented before/after examples, and makes sure an indented block renders as
  code.
- **Empty.** A release with no user-facing feature, fix or break says *No
  user-visible changes in this release* once, instead of three empty sections.
  A single empty section says *None in this release.*
- **Index.** It has:
  - a short generated intro;
  - a link to CHANGELOG.md on GitHub, for the full list including
    maintenance;
  - the toctree, newest first;
  - the line naming the earliest release and pointing at CHANGELOG.md for
    the ones before it.

### Wiring and freshness

- `docs/conf.py`:
  - add `"scripts.render_release_notes": "docs/release-notes/index.md"` to
    `_RENDERED_PAGES`;
  - update that dict's docstring so it names git history as a source.

  The render runs at most once per tag set. The renderer stamps what it
  rendered (the tag list with shas, plus a digest of the renderer,
  `release_events.py` and `cliff.toml`) and skips the roughly 9 s render when
  the stamp matches. Otherwise `nox docs`'s html + doctest pair renders twice.
- `docs/index.rst`: add `release-notes/index` to the Reference toctree.
- `.gitignore`: add `docs/release-notes/`, with the comment shape the other
  rendered pages use.
- **Make freshness.** `SPHINX_SRCS` gains the renderer, `release_events.py`,
  `cliff.toml` and a tag stamp file. The tag stamp is rewritten only when
  `git tag --merged HEAD` (names and shas) changes, so `make docs-html`
  rebuilds after a fetch adds a tag, and not on every commit. The stamp path
  works in worktrees (`git rev-parse --git-common-dir`).
  `tests/unit/docs/test_sphinx_srcs_cover_included_sources.py`'s rule
  applies.
- **Full history everywhere the docs build:**
  - `fetch-depth: 0` on ci.yml's `docs` job and release.yml's `docs` job;
  - a Read the Docs `post_checkout` job (`git fetch --unshallow --tags`, or
    the RTD-documented equivalent) in `.readthedocs.yaml`.

  The builder lists every other sphinx entry point (nox `docs`, `make docs`,
  `doctest`, tests that build pages) and confirms each one has history.
- **The repository URL.** The renderer reads it from `pyproject.toml`
  `[project.urls]`. `cliff.toml`'s template can't read pyproject, so a unit
  test pins the two spellings to agree. The test is a guard, not a second
  owner.

### The footer rule: `scripts/check_breaking_marks.py`

- The checker refuses every commit in the checked range that
  `release_events` lists as unremediated. The message names the commit and
  says to add a `BREAKING CHANGE:` footer telling users what to do, or saying
  plainly that nothing needs doing.
- It is enforced independently of the checker's merge and no-API-change
  early exits (`check_breaking_marks.py:~916`). A mark needs text whether or
  not the golden changed.
- A correction is a counted mark, so it needs its own footer text too.

### Documentation

- `docs/contributing.md`, breaking-change section:
  - the footer is required;
  - it is Markdown;
  - it is published word for word on the release-notes page, so it is
    written for users;
  - a maintainer-only scope is never breaking, and its scopes are listed in
    `MAINTAINER_SCOPES`;
  - link to the release-notes index.
- `docs/release_process.md`: the pages build from history at docs time, and
  there is nothing to regenerate.

## Tests

- **`tests/unit/scripts/test_release_events.py`:**
  - full footer text, multi-line and multi-paragraph, checked against the
    real git-cliff corpus;
  - two breaking footers on one commit;
  - the swallowed-trailer case is unremediated;
  - `Events.unremediated` is populated, and is not a refusal;
  - the maintainer-scope predicate, including comma scopes and unscoped
    commits.
- **`tests/unit/scripts/test_render_release_notes.py`,** run over a throwaway
  repo with real git-cliff, like `test_changelog_rendering.py`:
  - grouping;
  - maintainer commits dropped from both the lists and the breaking section;
  - a footerless row with a collapsed body and trailers stripped;
  - a correction, plus the back-reference on the target page;
  - escaping of `<host>`;
  - the empty-release line;
  - stale page removal;
  - the shallow refusal;
  - a stray `v`-containing tag is refused by name;
  - newest-first order across 0.9/0.10;
  - the stamp skip.

  A Sphinx `-W` smoke build of a generated page proves the markup builds.
- **`tests/unit/scripts/test_check_breaking_marks.py`:**
  - a `!` without a footer is refused;
  - `BREAKING CHANGE:` followed by only `Assisted-by:` is refused;
  - a footer-only mark passes;
  - a correction without text is refused;
  - a no-API-change commit with `!` and no footer is refused (independent of
    the early exit).
- The URL-agreement guard.

## Decisions made during the final review (2026-11-18)

- **`test` is a user-facing scope.** It names the `otto test` verb (28375f4eb
  removed `OttoSuite` and `--tests` under `feat(test)!`), so it is not in
  `MAINTAINER_SCOPES`. Harness work uses the scope `tests`, or the `test` type,
  which the changelog skips.
- **A breaking mark on a maintainer-only commit is refused.** It would bump
  the version but appear on no page. `Events.hidden_marks` holds these, and
  `make check-breaking` refuses them in the checked range.
- **Remediation that git-cliff would cut is refused going forward.** A
  wrapped line that starts with `word:` opens a new footer in git-cliff, and
  so in the model, which cuts the remediation short.
  `Events.cut_remediation` names that line, and `make check-breaking` refuses
  it. History keeps git-cliff's split: six old entries stay cut.
- **Commit text is checked against an allowlist, not escaped with regexes.**
  Each fragment, and each title once scope and subject are joined, is parsed
  with MyST's own parser using `docs/conf.py`'s extensions. Only plain
  Markdown passes. Anything else is shown verbatim as literal text, so
  nothing is ever dropped. The renderer refuses a finished page that holds
  any raw HTML other than its GENERATED header.
- **Smart quotes are off on these pages only.** A Sphinx transform runs
  before SmartQuotes, so `--wait` stays `--wait`.
- **The collapsed commit message strips only trailers** (`TRAILER_TOKENS`,
  matched case-insensitively), so `BREAKING:` and `Docs:` notes in old
  commits stay visible.
- **Pages carry a GENERATED header,** like the other rendered pages, so the
  docs linters skip them.
- **Commit-time check from an off-the-shelf linter** (Chris, 2026-11-18:
  prefer a common linter to custom scripts). The `.githooks/commit-msg` hook
  runs commitlint with only its built-in rule
  `breaking-change-exclamation-mark`, which requires `!` and a
  `BREAKING CHANGE:` footer together. No other commitlint rule is enabled.
  `make check-breaking` stays the authority at push and in CI, and alone
  catches the empty footer, the maintainer-scope mark and the cut
  remediation. The behaviour test is vitest in the web lane, because the
  hostless pytest jobs have no `node_modules`.
