# Agent Info

- Read the documentation in `docs/_build/html` for a high level understanding of `otto` (if they don't exist, run `make docs`).
- Consider scalability and maintainability whenever possible.
- If the user reports a bug, reproduce it with unit/integration tests first, then fix it, then run the tests again to prove it is fixed.
- Do not use threads combined with asyncio. also, an event loop is guaranteed within the Typer subcommands (e.g. run, test, monitor)
- `ty` is the type checker available here — run `make typecheck` to verify type correctness
- Gates are scoped by the diff, and only the TIP of a landing is gated. Whatever reaches `main` in one push — one squash, or several commits that persist one by one — runs `make gate-scope`'s **tip** list once, on the final tip, over the whole base..tip diff. Every commit before the tip, persisting or not, runs only the tests in its likely breakage areas plus ruff on the files it changed: no gate, no escalation consideration, no per-commit lanes. The oracle's commit list is a working check while you build a commit, never a landing gate. Commit first — `gate-scope` refuses a dirty tree. The lanes it names assume the dev VM (lab VMs for integration and bed roots, `make web` for the dashboard). Unsure → `make gate-scope` is the answer, not a bigger gate. Stability soaks are never a gate lane: the oracle names only single passes, and docs/contributing.md's stability-lanes rule says where. The test-isolation guard (`nox-unit-repeat`) is CI's `unit-repeat` job, run after the push, never a local gate. The landing's tip is what is gated and stamped: `make gate-tip` runs the oracle's tip lanes and stamps the committed tree per lane, and a push to `main` refuses a tip whose lanes are not stamped (the history checks and docs run at the push itself).
- Documentation is a high priority. See docs/contributing.md for documentation guidelines.
- Do not worry about backwards compatibility at this time.
- ONE DECISION, ONE PLACE. The defect class that makes this code unmaintainable is not copy-paste; it is the same decision computed independently at two entry points: a constant restated where another site calls a resolver, an open/teardown sequence re-spelled with a subset of its steps, a command string rebuilt by hand, a retry or poll loop hand-rolled beside `otto.utils.wait_for`, a constructor call repeated so a new field must be added twice. A systemic fix then lands in one copy and silently misses the rest. Therefore:
  - Before writing a resolver, builder, sequence or loop, name what it decides (a deadline, a login budget, a compose command, the session open order) and grep for the site that already decides it. If one exists, call it; if it lacks a parameter you need, add the parameter there rather than restating the logic here. If none exists and this is the second place that needs it, extract the shared function first, then call it from both.
  - When two entry points must behave identically on the same input (run vs login, declared vs discovered port, compose_up vs deploy), they share one function and a test drives both through it with the same input. A call-point deviation — the same input behaving differently from two entry points — is the signature of a divergent implementation, never a local bug: consolidate on common code, do not patch the deviating site.
  - When fixing a shared decision, grep for every other site that makes it before closing the item, and move them onto the fix. "Fixed here, the other copy is a follow-up" is not done.
  - This is not a licence for Swiss-army-knife functions. A shared function has one job; its parameters are the sanctioned variation. Two callers that need different behaviour get two small functions over one common core, not a flag soup — but the core is still one function.
  - Reviews name every new function, sequence or constant that restates one that already exists, with the existing site's path. Textual clone detection does not find this class; only the grep above and the review do.
- If a work item from the `todo` directory is completed, delete the file when 100% complete. If a todo file is only partially copmlete, mark the items as done with a checkmark emoji and summarize what is left to do
- When working in a git worktree (`.claude/worktrees/*`), treat the main checkout at the repo root as READ-ONLY: every edit, test run, and commit happens inside the worktree. Never write through absolute paths into the main checkout — stray edits there create unstaged noise and block the eventual merge with untracked-file conflicts.
- When work in a worktree is ready to hand back — and always before any squash onto `main` — run `make gate-fresh`. Both the main checkout and your worktree accumulate gitignored build artifacts (notably `src/otto/_webassets/*/`, built only by `make web`) that CI does not have, so a green local run can certify an environment CI will never reproduce. `gate-fresh` re-runs CI's assets-absent Python lanes against your **committed** tree in a throwaway pristine worktree. It refuses if tracked files are modified or staged — commit first, then gate.
